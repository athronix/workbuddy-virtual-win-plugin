### 17:2x 用户纠正 hish-bridge 模型（重要，推翻 16:1x 结论）
- **错误结论（16:1x）**："hish 引擎跑在 WB 沙箱、与 WB 同 uid、hish 只是 WB 内全功能 shell、不需要 HiShell" —— **错**。
- **正确模型（用户指正 + SKILL.md 架构图/已知局限佐证）**：hish-bridge = **共享用户目录（`~/hish-bridge/v2/`，hmdfs）上的文件命令总线**。WB 侧是**工具** `hishctl`（写 `task.json` 到 `inbox/`、读回执）；HiShell 侧是**服务** `service.py`/`service.sh`（监听/执行/写 `tasks/<id>/{status,stdout,stderr}`）。**主部署服务在 HiShell（uid 20020099）**；`doctor --fix` 只能在 WB 沙箱内拉起**回退实例**（uid 20020171，即 pid 36182）——那只是 fallback，不是全部。我用"看到 pid 36182 在 WB uid"误判了全貌，`/proc` 因 hidepid 只显示本 uid 进程，HiShell 侧服务（另一 uid）本就看不着。
- **跨 App 判活**：`kill -0` 抛 `EACCES(13)` = 进程在但无权信号 ≠ 死；`ESRCH` = 死。WB 对 HiShell 服务 `kill -0` 即 EACCES，误判会令 WB 拒投任务。
- **用户新提案（待评估）**：仿 hish-bridge 造反向桥 `workbuddy-bridge`——**服务跑在 WB**（监听 `~/workbuddy-bridge/v2/`、在 WB 沙箱执行命令）、**工具跑在 HiShell**（`wbbctl` 写任务/读回执），让人类在 HiShell 终端即可配置/定制 WB 的执行环境（重建插件、重启隧道、跑测试、查 WB 状态）。传输对称（仍是 `$HOME` hmdfs），复用 hish-bridge 的 v2 协议/服务代码即可，需加 token 校验防其它 App 借 `$HOME` 注入命令。

### 18:3x 用户深挖鸿蒙沙箱机制 → **复核实测推翻旧"ELF 不可执行"结论**
- **旧结论（17 及之前记忆）错误**："系统目录 ELF 不可执行 / 用户目录 ELF 不可执行、shebang 跑不了（hish-bridge 根因）" —— **本机实测均不成立**。
- **新实测事实（本机 HarmonyOS NEXT PC）**：
  - **execve 系统 ELF 被允许**：`/bin/sh`（= `/system/bin/sh`，symlink `/bin→/system/bin`）和 `/system/bin/true` 均可执行并正常返回（timeout 包裹 exec 退出 0、sh 打印输出）。
  - **`#! /bin/sh` shebang 脚本可跑**：仓库内 `.__shb_test__.sh`（`#!/bin/sh` + echo）直跑打印 `SHEBANG_OK`。
  - **用户目录 ELF 可直跑（决定性）**：把 bundle `node`（`/data/storage/el1/bundle/libs/arm64/node/bin/node`，可读可 exec）`cp` 到仓库目录 `.__node_local__` 后直接 `./.__node_local__` → 打印 `USERDIR_ELF_RUNS v24.13.0`，exit 0。
  - **真正的 MAC 限制是"读"不是"执行"**：`cp /system/bin/true`、`ls -l /system/bin/ls`、`cat` 系统 ELF → `Permission denied`（open-for-read 被拒）；但 `execve` 允许。`ls -lL /system/bin/true` 偶发可读（策略不一致）。
- **顺带发现真 bug**：本机 **brokered shell 的 rm shim 已坏**。`safe-bin/rm`（及 unlink/rmdir）的 shebang 是 `#!/bin/bash`，但本机**只有 `/bin/sh`、无 `/bin/bash`**（`ls /bin/bash` → No such file）→ 调 `rm` 报 `bad interpreter: No such file or directory`、exit 126 失败。所以本机经 brokered shell 的 `rm` 会失败，须用 `node -e fs.unlinkSync()` 或走 hish 真删。（cp/mv/ls 未被覆盖、正常。）
- **结论修正**：hish-bridge 的存在根因**不是**"ELF 跑不了"，而是 **App 沙箱无法跨 App 读数据 + WB 的 brokered 安全层 + 真机包管理（brew/git）需求**。已在 MEMORY.md 把三处旧 ELF 结论更正，并补 rm-shim 坏笔记。
- **清理**：`.__node_local__` / `.__shb_test__.sh` 用 `node fs.unlinkSync` 已删（因 rm 坏）。
