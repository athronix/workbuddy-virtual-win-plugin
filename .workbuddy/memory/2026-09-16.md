## GUI 解锁排查（2026-09-16 19:4x，用户在 VM 桌面实测）

### 现象
用户在 VM 桌面 PowerShell 跑 §4 的「GUI 重启块」后，`/health` 仍 `interactive=false / state=degraded / desktop=unknown / windowStation=W`，重启无效。

### 根因（两个叠加，均非用户操作问题）
1. **孤儿 node 逃过 `schtasks /end`**：`start-hidden.ps1` 用 `Start-Process -WindowStyle Hidden` 拉起 node，node 脱离 powershell 父进程成为孤儿；`schtasks /end` 只杀 powershell 壳，node 仍占 18443。新 `schtasks /run` 实例因端口被占绑定失败退出 → 旧 degraded node 一直服务。
2. **`Stop-Process -Id $p` 参数绑定失败**：原清理命令 `$p = (...).OwningProcess | Select-Object -Unique; if($p){Stop-Process -Id $p}` 中 `$p` 是**对象**，`-Id` 收不到整数 PID → 静默失败，node 没被杀。

### 实证（VM 上 `Get-Process node`）
三个 node 全在 SessionId=1、全以 `YQWANG-HOS-SANW\User` 运行、explorer 在 session 1、LogonUI=0（未锁屏）。→ **登录方式/交互条件本就满足**，降级纯因「服务没真重启」。最新 node 启动时间停在 `18:38:45`（setup.mjs --apply 那次），19:37 的 schtasks /run 没产生新进程（坐实端口冲突退出）。

### 修复
- 文档 §4 重启块改为：`$pids = @(... | Select-Object -ExpandProperty OwningProcess -Unique); if($pids.Count){$pids|%{Stop-Process -Id $_ -Force}}`，并补成因注释。
- 给用户同一修正块（先 ExpandProperty 取 PID 杀端口占用、确认端口释放、再 schtasks /end + /run、验证新 node 启动时间 + health 翻 interactive=true）。

### 待用户回执
用户尚未回贴修正块第 4/5 步输出。预期：新 node 启动时间为重启时刻、`interactive=true`。若仍 degraded，则需看任务登录方式（但实证已排除 session 0/System 假设）。

### ⚠️ 结论被推翻 + 真根因（读源码后，2026-09-16 19:56）
用户最新实测：即便用 `-ExpandProperty` 正确杀掉占 18443 的 node（PID 11580）并 `schtasks /run` 重启，`/health` 仍 `interactive=false / windowStation="W" / desktop="unknown"`。**旧结论「降级纯因服务没真重启」错误**——重启无效是因为根因不在"起没起"，而在"怎么起"。

**读 `packages/vm-capabilities/psmod/gui.ps1` 得触发机制：**
- `Get-SessionHealth`（gui.ps1:15-75）：`$interactive = ($sessionId -ge 1) -and ($ws -eq 'WinSta0') -and $explorerAlive`（**gui.ps1:42**）。三者 AND。
- `windowStation`/`desktop` 来自 `GetUserObjectInformationW(GetProcessWindowStation(), n, …)`：`$ws` 用 `n=2`（UOI_NAME，正确）；`$desktop` 用 **`n=7`（非标准索引，应 n=2/3）→ 调用失败 → desktop 永远 "unknown"**（gui.ps1:38，潜在 bug，但不参与 interactive 判定）。
- `windowStation` 实测为 `"W"` ≠ `"WinSta0"` → 整条判死，与 sessionId=1/explorer 在跑无关。

**真根因（窗口站脱离）**：VM 启动链 `schtasks(WinVMBridge.Service)` → `powershell -WindowStyle Hidden -File start-hidden.ps1` → `Start-Process -WindowStyle Hidden node`。计划任务动作（即便"仅当用户登录时运行"）跑的是**无交互桌面连接的隐藏 powershell**，它再 Start-Process 出的 node **继承"无交互桌面"窗口站**，而非 `WinSta0\Default`。`cli.ts` 头部铁律要求"必须在交互式桌面会话内启动"——隐藏 schtasks 包装违反此铁律，故 windowStation≠WinSta0、interactive 恒 false。**重启只是用同一坏链再生一个"无桌面 node"，故循环无效。**

**决定性诊断 + 修复方向（已交用户验证，未回贴）：**
1. 在 VM 交互 shell 跑同款 P/Invoke 确认 `YOUR_SHELL_WS=WinSta0`（证明 shell 在交互桌面）。
2. 从交互 shell `Start-Process node -ArgumentList <node 参数>` 拉起（继承 WinSta0\Default），重查 health 应翻 `interactive=true`。
3. 永久修复：把服务启动从 `schtasks` 隐藏包装改为**交互桌面启动**（用户 `shell:startup` 启动文件夹 / `Run` 注册表键 / 托盘自启），使其作为普通交互桌面程序起来（天然在 WinSta0\Default）。同步修 gui.ps1 `n=7`→`n=2`。

**经验**：GUI 降级排查应**先读 Get-SessionHealth 源码定性**（三条件哪个挂），而非盲目循环重启；隐藏 schtasks 启动链与"必须在交互桌面"铁律根本冲突，是本类部署的架构性坑。
