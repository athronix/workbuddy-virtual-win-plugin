## 9. 推送凭据：两个坑，都不是记忆里写的那样

### 9.1 `~/.gitconfig` 的 insteadOf 会把 HTTPS 静默改写成 SSH（新坑）

```ini
[url "git@github.com:"]
    insteadOf = https://github.com/
```

后果：所有 `https://github.com/...` 推送**全部走 SSH**，于是持 PAT 也没用，
报 `git@github.com: Permission denied (publickey)` —— 看起来像"token 无效"，
实际是**根本没走 HTTPS**。

- ❌ `-c "url.https://github.com/.insteadOf="` **无效**（git 不支持空值移除规则）
- ❌ `-c core.sshCommand=` 传空值 → `error: cannot run : No such file or directory` / `fatal: unable to fork`
- ✅ **正解：`GIT_CONFIG_GLOBAL=<干净配置文件>`** 绕开整个 `~/.gitconfig`
  ```bash
  printf '[user]\n\tname = X\n\temail = Y\n' > "$HOME/wbtmp/gitconfig-clean"
  GIT_CONFIG_GLOBAL="$HOME/wbtmp/gitconfig-clean" GIT_ASKPASS=... git push https://github.com/OWNER/REPO main V1.4.40
  ```

### 9.2 本仓在两个 GitHub 仓 + 两个 Gitee 仓，共 **4 个分发端点**

| 端点 | 角色 | 凭据 |
|---|---|---|
| `athronix/...` GitHub | 开发源仓（git remote origin）| `GITHUB_PAT`（对该仓 push=true）|

## 10. ★ I-38.6：`export { X } from './m.js'` 不建立本地绑定（P0 阻断）

V1.4.38 真机部署 4a 步直接崩：

```
ReferenceError: resolveTunnelIdentityFile is not defined
    at ssh2Creds (delivery/setup.mjs:320)
```

阶段 5.1 把私钥探测链下沉到 `connect-channel.mjs` 时，`setup.mjs` 只写了：

```js
export { resolveTunnelIdentityFile } from './connect-channel.mjs';   // ← 只挂导出表
```

而 `:320`（`ssh2Creds`）和 `:1321`（OH 宿主隧道分支）**在模块体内直接调用它** ⇒ 一调就炸。

- **`export … from` = re-export，只往导出表挂名，不建模块内绑定**。
- 诡异点：`import * as m from './setup.mjs'` 能拿到这个符号，`m.resolveTunnelIdentityFile()` 也**能调通**
  ⇒ **任何「导出可用」的验证都发现不了它**，只有走内部调用路径才炸。
- 修法：补 `import { resolveTunnelIdentityFile } from './connect-channel.mjs'`，
  re-export 改成 `export { resolveTunnelIdentityFile };`（本地转发）。

**守卫**：`tests/unit/setup-reexport-binding.test.js`（4/4），判据全行为性。第 ③ 条
「有调用就必须有 import」已在**真实缺陷态反向验证会红**（报「2 处调用但缺 import 绑定」）。

## 11. ★ I-38.7：上游面引擎误注入 vm registry —— 比裸奔更隐蔽（P0）

V1.4.39 部署后实测：

```json

=> {"ok":false,"error":{"code":"POLICY_DENIED","message":"能力未注册：browser.meta.eval"},
```

对照：`server.ts:648` 的 vm 面引擎**必须**传 registry，两者各司其职。

**守卫**：`step32-upstream-gate.test.js` 新增「禁止注入 registry」（24/24），已突变反证会红。

（Gitee release 列表共 19 个，最高只到 V1.4.38）。

### 为什么会误判（这是本条最有价值的部分）

**tag ≠ release ≠ 资产，三段完全独立。**
`git ls-remote --tags` 明明能看到 `V1.4.40 → 449f4cc` 已推到 athronix Gitee，
于是「tag 在 ⇒ 以为整条链在」。实际上 tag 只是个 ref，**release 是另一套 API 对象**，
资产还要再 attach 一次。查 tag 存在**永远证明不了** release 存在。

### 两个叠加坑

1. **athronix GitHub 的 SSH 钥从来没 push 权**：`id_ed25519` 对
   `git@github.com:athronix/...` 报 `Permission denied (publickey)`。
   该端点**一直**是空的，只是没人逐端点验过。
2. **`~/.workbuddy/credentials.env` 里带连字符的键 shell 无法 source**：
   `GITHUB_PAT_SANWAY-TECH` / `GITEE_PAT_SANWAY-TECH` / `GITHUB_GRAINED_PAT_SANWAY-TECH`
   source 时全报 `command not found`（`-` 不是合法变量名）。
   ⇒ 这 3 个 token **一直躺在文件里但从没被加载过**。
   本轮绕过方式：`GITHUB_PAT`（对 athronix `admin=true/push=true`）+ `GITEE_ACCESS_TOKEN`。
   **待改**：键名换成 `_SANWAY_TECH`。

### 修复与验证

`publish-release.mjs` 本身支持 `--repo`，且 release 走 **HTTPS API**，不吃 SSH 权限：

```
GH_TOKEN=$GITHUB_PAT node delivery/publish-release.mjs \
  --tag V1.4.40 --zip release/V1.4.40/winvm-overall-V1.4.40.zip \
  --repo athronix/... --apply --mirror-gitee
```

V1.4.39 / V1.4.40 各补 1 个 GitHub release + 1 个 Gitee release（各 4 资产）。
**验证不看日志、只看实测**：8 端点全部 200/206，且远端 `.sha256` 与本地
**逐字节 SAME**（`V1.4.39=b8ee74cb…` / `V1.4.40=5c378144…`）。

### 教训

> **「日志说成功」与「端点可下载」之间还差一次匿名实拉。**
> 上一轮我在台账写「已补齐 4 端点」，依据是 `publish-release` 的 `✓` 行 ——
> 但那次 `--repo` 只跑了一个仓，`✓` 只证明**那一个仓**成功。
> 凡「N 个端点」类断言，必须**逐端点 loop 实测**，不能由单次成功的日志外推。

## 16. `download-verify.sh` 诊断加强（I-38.8 收尾）

原来失败只有一行 `DOWNLOAD_FAILED 双源均不可达（网络？tag 不存在于两端？）`，
发错仓时**无法区分**是「仓错了」还是「tag 不存在」还是「传输层断流」。
（V1.4.38 那次就是 13 行 404，排查了半天才发现是 athronix vs sanway-tech。）

改动 `~/.workbuddy/skills/winvm-plugin-deploy/scripts/download-verify.sh`：

1. `REPO` 改 `REPO="${VM_REPO:-sanway-tech/...}"` —— 保持单点（gitee/github 共用），
   但可被 `VM_REPO` 覆盖以便灰度/私有镜像；正常发版**不要**改。
2. 失败分支逐端点打 `REPO / TAG / 资产名 / HTTP code`，并按码分三支：
   - `404` → 明说「该 tag 在此仓无此资产」+ 提示先查是否上架到 sanway-tech（不是 athronix）
   - `200/206` → **资产可达**，失败属传输层（断流/超时/磁盘），别去查仓
