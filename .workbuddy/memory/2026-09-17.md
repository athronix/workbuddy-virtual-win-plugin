# 2026-09-17 工作日志

## GUI 降级根因定位 + 修复（真 bug，非操作问题）

### 现象
部署后 `/health` 一直 `session.interactive=false / state=degraded`，GUI 域被门禁。
用户 RDP 进 VM 桌面、反复 `schtasks /end`+`/run` 重启服务，仍 `degraded`。

### 决定性诊断（用户在 VM 桌面 PowerShell 实测）
```
YOUR_SHELL_WS = [W]   # 用户自己的交互 shell 也读出 "W"
```
用户明明在交互桌面（可见 PowerShell、explorer 在 session 1、未锁屏），窗口站却读成 `"W"`。
与 node 进程 health 的 `windowStation:"W"` 完全一致 → 说明**会话本就是交互式**，但判定逻辑把 `"W"` 和字面量 `'WinSta0'` 比 → 恒 false。

### 真根因（gui.ps1）
`packages/vm-capabilities/psmod/gui.ps1` 的 `Get-SessionHealth`：
- L36/38 用 `GetUserObjectInformationW(UOI_NAME=2)` 经 `StringBuilder` 读窗口站/桌面名，本机实测读出 `"W"`（应为 `"WinSta0"`）——P/Invoke 封送假值。
- L42 `$interactive = ($sessionId -ge 1) -and ($ws -eq 'WinSta0') -and $explorerAlive` → 因 `$ws="W"` 恒 false。
- L38 桌面读取用 `n=7`（非法 UOI 索引，应为 2）→ `desktop` 永远 `"unknown"`（副 bug，不参与判定）。
→ 重启无效：每次重启都用同一套隐藏启动链重新生成「读出 W 的 node」，判定照样 false。**是假阴性，不是真降级。**

### 修复（源码已改）
`gui.ps1` 判定段改为用 `OpenWindowStationW('WinSta0', $false, WINSTA_READATTRIBUTES)` 实测当前进程能否打开交互窗口站：
- 交互会话内进程可成功（返回非 NULL）→ `canReachInteractive=$true` → `interactive=$true`；
- session 0 服务打不开 → false。不依赖字符串读取，规避封送假值。
- 顺手把 `$ws`/`$desktop` 在命中时置 `'WinSta0'`/`'Default'`。
- 部署机制：`install-vm.mjs` 在 VM 内 `npm run build` + 把 `packages/<pkg>` junction 链接；VM 服务读的是 `packages/vm-capabilities/psmod/gui.ps1` 源文件。host 重跑 `setup.mjs --apply` 会重推 `packages/` 树并重启 → 带上修复。

### 落地方式（给用户）
1. 决定性探针：`OpenWindowStationW('WinSta0')` 在 VM 交互进程返回非 NULL → 证明修复逻辑成立；
2. 直接补丁：VM 上用 node 脚本对 `C:/WinVMBridge/packages/vm-capabilities/psmod/gui.ps1` 做确定性字符串替换（规避 PowerShell 转义），替代 `GetUserObjectInformationW` 比较；
3. 或宿主 `node delivery/setup.mjs --apply` 重推（权威、已验证可重跑）。
重启服务后 `/health` 应见 `interactive=true, windowStation=WinSta0`。

### 文档
`docs/oh-host-install-run-test.md` §4 GUI 降级段已订正：旧「RDP 登录 + 重启解锁」是错的，改为「改判定逻辑（OpenWindowStationW）」，保留端口清理 `-ExpandProperty` 陷阱提示。

### 教训
- 不要轻信 health/状态字段的字符串值（窗口站名被封送成 `"W"`）；用「能否真正打开对象」做能力探测更稳。
- 用户质疑"反复重启没用"是对的——应先读源码确认触发条件，而非让用户空转。

## GUI 重启空转根因终判 + 源码修复（2026-09-17 下午，用户贴 4 段诊断后闭环）

### 用户 4 段诊断（VM 桌面 PowerShell，决定性）
1. `/health`：`session.sessionId:0, windowStation:"", desktop:"", interactive:false, state:"unavailable"`；`psBridge.state:"ready", uptimeMs:15534106`（≈4.3h）。
2. 占 18443 的 node：**PID 7992, SessionId 1**（正确交互会话，非 session 0）。
3. ps-bridge 常驻 powershell：PID 5704/10504，**均 SessionId 1**，父=node 7992（进程树正确）。
4. 任务登录方式字段为中文，findstr 英文未命中；但由 SessionId=1 + 交互用户可判为 InteractiveToken。

### 机制复审结论（推翻"重启即可"旧假设）
- **服务确在 session 1（正确）**，非 session 0 → 之前"重启让交互 shell 重跑"的假设方向对、但执行一直无效另有原因。
- `state:unavailable`+空 `windowStation` = 探针 `catch` 兜底（index.ts:50）= `bridge.call('gui','Get-SessionHealth')` 抛 `PsBridgeError`（gui 命令返回 `ok:false` 或超时）。
- **ps-bridge 预加载且不可热更**：`ps-bridge.ps1` 启动 `dot-source` 全部模块（`Set-StrictMode -Version Latest`）；`Import-CapabilityModule` 对非预加载模块抛 `MODULE_NOT_PRELOADED`。→ 盘上 `gui.ps1` 改了，但 **4.3h 常驻进程吃的是旧模块态**，直调 healthy 是因为新开进程吃到新文件。
- **重启空转真因 = 孤儿 node 陷阱**：`start-hidden.ps1` 用 `Start-Process -Wait node` → 任务动作进程常驻 Running；`schtasks /end` 只杀 powershell 包装层，node（Start-Process 子进程）游离成孤儿继续占 18443；后续 `/run` 被 `MultipleInstancesPolicy=IgnoreNew` 吞掉、或新 node `EADDRINUSE` 秒退 → 旧进程独活、旧 gui 代码继续服务。`uptimeMs` 一直不归零就是铁证。

### 源码修复（install-vm.mjs，已落地）
1. 任务 XML `MultipleInstancesPolicy`：`IgnoreNew`→`StopExisting`（/run 必停旧启新，不再被吞）。
2. `start-hidden.ps1`：**前置按端口强杀旧实例**（`Get-NetTCPConnection -LocalPort $svcPort` → `Stop-Process`）+ `finally` 兜底杀 node（`-PassThru`+`WaitForExit`），从源头消除孤儿与 EADDRINUSE。
3. `killServiceProcess`：除端口占用外，同时杀 `CommandLine -like '*start-hidden.ps1*'` 的 powershell 包装进程。

### 用户侧立即修复（VM 桌面，管理员 PowerShell）
```
# 1) 杀孤儿 node（端口）+ 启动器
$p=(Get-NetTCPConnection -LocalPort 18443 -EA 0).OwningProcess | Select -Unique
if($p){Stop-Process -Id $p -Force -EA 0}
Get-CimInstance Win32_Process -Filter "Name='powershell.exe'" -EA 0 | ?{$_.CommandLine -like '*start-hidden.ps1*'} | %{Stop-Process -Id $_.ProcessId -Force -EA 0}
# 2) 重注册任务（用已改好的 install-vm.mjs，含 StopExisting+自清理启动器；跳过慢步骤）
node delivery/install-vm.mjs --skip-install --skip-build
# 3) 启动（自清理会再杀一次端口，确保干净）
schtasks /run /tn WinVMBridge.Service
# 4) 复核：期望 sessionId:1, windowStation:'WinSta0', interactive:true, state:'healthy'
node -e "fetch('http://127.0.0.1:18443/health').then(r=>r.json()).then(j=>console.log(JSON.stringify(j.session))).catch(e=>console.log('ERR',e.message))"
```

### 教训
- "反复重启无用"= 机制 bug（孤儿进程 + IgnoreNew），不是用户操作问题，**不该让用户空转**。
- ps-bridge 模块预加载无热更 → 任何 .ps1 能力修复必须先重启 ps-bridge（= 重启 VM 服务），这是硬约束，应在文档/改动说明里显式点明。

### D25（新 P1，比原 D16 更危险）：`app.winget.search` 静默返回空
- 现象：插件 `ok=true, data=[], warnings=[]`；同 VM 直接 `winget search 7zip` **有 11 条**。
- **根因（二分证明）**：`psmod/app.ps1` 的「按分隔线定宽列」**逻辑不可能工作**——winget 分隔线是**一条连续长横线**（98 个 `-`），`[regex]::Matches($s,'-+')` **只得 1 个匹配** → `$cols.Count=1` → 每行都命中 `if ($vals.Count -lt 3) { continue }` → `$out=@()`。
- 修法：由**分隔线上一行表头**的 `Name|Id|Version|Match|Source` **起始索引**定列边界（`qa/probes/bisect-d16.mjs` 分支 B 实测解出 11 条，含空格的 `name` 也正确）；并**fail-loud**：有数据行却解析出 0 条 → `throw 'WINGET_PARSE_FAILED: <首行原文>'`。
- **通用教训（跨会话可复用）**：解析外部命令表格输出时，**「静默给空」比「报错」危险得多**（调用方会误判"不存在"）。凡"存在真实数据却解析出 0 条"必须抛错。与 D21（inventory 19→1 静默漏报）同类。

- **发现路径（重要方法论）**：交叉审计「客户端 `tools/list` 里 54 个能力只有 27 个声明 `required`」→ 逐一把这 27 个映射回 psmod 函数查 `Mandatory` → **结论是无声明缺失**（`Get-ScheduledTaskInfo`/`Get-LocalUserInfo`/`Get-EnvironmentVariableInfo`/`Get-InstalledApps`/`Get-AppxPackageInfo`/`Get-AppOpState`/`Send-KeyboardInput`/`Get-UiaTree` 等均无必填）。**差点把「27 个无 required」误报为 schema 缺陷。**

  - `system.process.list {"top":"abc"}`（schema `integer`）→ `EXECUTION_FAILED`，message=ˊ无法将值"abc"转换为类型"System.Int32"ˊ

### 方法论（跨会话可复用）
- **审计某个断言的覆盖面时，要连带问「这个校验总共覆盖了哪几个维度、漏了哪几个维度」**。只数「有多少能力没被保护」会把正确结论引向错误归因；正确的问法是「校验做了哪几件事」。
