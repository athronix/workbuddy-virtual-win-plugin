## 2. 判据原文摘录与链路复推（离线，逐锚点）

### 2.1 信封 `ok=true` 的真实语义（C0 病灶：名实断点在观测面，不在 psmod）

数据流（A2A 委派重放路径）：

```
psmod 回执对象 R = { id, dryRun, exitCode, success, verified, fallbackUsed, output, [residualEvidence] }
  → provider.execute：res = { ok: true, data: R, ... }          // index.ts:551 —— res.ok 只表达「调用完成无错」
  → server.ts:1309-1314：isError = !res.ok; structuredContent = { ok: res.ok, data: res.data, ... }
  → toExecutedResult（approval-replay.ts:214-241）：
        ok = isError !== true && sc.ok === true                 // 只看服务端信封 ok
        summary = `${capabilityId} 执行成功`（无 data.summary 字符串 ⇒ 兜底文案；
                   summaryFromData 只收 string，uninstall 的 output 是数组 ⇒ 不命中）
```

**结论（静态可证）**：`res.ok`（信封）= 「能力被成功调用」（未抛异常/策略通过/桥有回执），`data.success`（回执）= 「K6 核验通过」——两者之间**没有任何折叠点**。全链路 `grep ".success"`（server.ts / adapter / framework / approval-replay）**零命中**，`success=false` 的回执照样产生信封 `ok=true`。审计链同样不存载荷（`result: { ok:true, summary }`，index.ts:542），`receiptCache` 存 data 但重启即失（server.ts:629，批13 已过夜不可追）。

⇒ **「ok=true（K6 语义=exit0∧核验过）」这个等式本身不成立**。V19 的第一候选解释不是核验判据有洞，而是**观测面语义断链**：seq26 回执很可能 `success=false` + `verified` 三态有 false + 带 `residualEvidence`，但委派回执/链摘要把它压平成了「执行成功」。若此说成立，真正的产品缺陷是「uninstall 回执 `success=false` 时 A2A 摘要仍报『执行成功』且宿主侧无一字转呈」（description 明令「宿主必须如实转呈，不得改写为成功」——summaryFromData 不读 output 数组，转呈面在委派通道上落空）。**注意**：仍需真机分叉（§4）确认当次回执到底是 true 还是 false，不冒判。

**旁证（证据文件自身，离线可查）**：`qa/p5-batch/b13/uninstall-final.json` 的完成回执步是**合成步骤形态**——`steps[0].capabilityId='appops.workflow.run'`、`ok:true`、`summary='app.winget.uninstall 执行成功'`、无 `data.success/verified` 任何一键（LLM 常驻回合收口 = bridge.ts:1548-1567 合成步骤，`ok:true` 是回合级恒值）。批13 采集脚本据以写下「ok=true」——它读到的从来不是 K6 核验位。**全 Node 链 `grep -w success`（server.ts / approval-replay.ts / adapter×3 / mcp-framework / ps-bridge.ts）零命中** ⇒ 折叠点在 Node 侧任何位置都不存在。真实 K6 位只存在于回执 `data` 内，而该 data 在委派通道被压平后不落链（审计仅 summary）、不落盘（receiptCache 重启即失）——当次真值已不可追，**只有真机复采（S4）能定性**。

**限定（不夸大 C0）**：委派内层回连（经 `/mcp?dtid=`）的 LLM 运行时**能**看到完整 `structuredContent.data`（含 `success/verified`）——若当次回执真是 `success=false`，LLM 理论上应把它转呈进回合文本；批13 回合文本未转呈 ⇒ 要么回执真是 true（C0 被证伪、H1/H2 上位），要么 LLM 漏报（另一观测缺陷）。**S4 复采用 MCP 直调拿原始 data，不依赖 LLM 转呈**。另注：重放路径（seq26 本体，approval-replay `toExecutedResult`）的 `ok` 同样只看信封——该路径连 LLM 都不经过，`success=false` 的回执在此 100% 被记作「执行成功」。

### 2.2 K6 三态判据（`psmod/app.ps1`，实测行号）

`Test-UninstallState`（:599-665）：

| 态 | 初始值 | 判定式 | 「空真」通道 |
|---|---|---|---|
| `registryGone` | — | `(-not $stillLookupFailed) -and ($null -eq $still)`（:616） | **卸载前就查不到键 ⇒ true**（"键从未匹配到"与"键已消失"不可区分；`$Entry=$null` 时预捕获同样查不到） |
| `exeGone` | `$true`（:619） | 仅当 `$root` 派生出**且** `Get-PackagePrimaryExeName` 取名成功才被重算（:647-657）；`$root=''` ⇒ 保持初始 true | **安装根派生不出 ⇒ 恒真**（`else` 分支根本不碰） |
| `dirGone` | `$null`（:620） | 仅当 `$root` 非空才置布尔（:643）；否则保持 `$null`=「无从核验」 | **派生不出 ⇒ $null 不阻断通过**（R-3 硬约束 :663：不做全盘扫描） |

`Test-UninstallVerificationPassed`（:671-678）：`registryGone ∧ exeGone ∧ (dirGone=$null ∨ dirGone)` ⇒ **当 `$root=''` 且重查查空 ⇒ 三态 = (true, true, null) ⇒ passed=true**。

关键辅助面：
- `Get-PackageInstallRoot`（:482-498）：① 注册表 `InstallLocation` 非空即用；② 否则从 `UninstallString`/`QuietUninstallString` 反推 exe 所在目录；③ **msi 型禁止反推**（:487）。全空 ⇒ 返回 ''。
- `Get-UninstallInstallerType`（:461-476）：entry=$null ⇒ `'unknown'`；含 msiexec ⇒ `'msi'`；有 QuietUninstallString ⇒ `'other'`；UninstallString 指向 uninstall.exe 且无 Quiet ⇒ `'nsis'`；其余 `'other'`。
- `Get-PackageUninstallEntry`（:524-591）打分匹配（5 键名≡Id / 4 键名含 Id / 3 DisplayName 归一≡wingetName / 2 互相包含 / 1 末段匹配）；**score=0 即不参与**——归一化只留 `[0-9a-z\u4e00-\u9fff]`（Get-NormalizedPackageName :151-156）。
- 回退面（:1006-1024）：`installerType -ne 'nsis'` **永不回退**，核验未过直接 `success=false` + `residualEvidence`。
- `app.inventory.list` 数据源（`Get-InstalledApps` :19-101）：**同一组三 hive** Uninstall 键（HKLM / HKLM\WOW6432Node / HKCU），按 `(name,version)` 分组合并，带 `registryKeyCount` 原始条数与 `installDate` 原值。**无任何缓存**（每次现扫，进程内缓存仅 system.network.config 有）。

### 2.3 portable 包（winget 合成登记）与判据的交叠

`BurntSushi.ripgrep.MSVC` 为 winget portable 型：winget 把包体落 `%LOCALAPPDATA%\Microsoft\WinGet\Packages\BurntSushi.ripgrep.MSVC_*\`、以链接暴露 `%LOCALAPPDATA%\Microsoft\WinGet\Links\rg.exe`，并在注册表 Uninstall 键写**合成登记**（键名含包 Id，DisplayName≈`RipGrep MSVC`，`UninstallString` 回指 winget）。批13 inventory 显示 `installDate=20260921`——9 月 21 日的旧值。两种子形态决定判据走向：

- **若合成键存在且匹配可得**：`Get-UninstallInstallerType` 对 `UninstallString="winget.exe" uninstall --id …` 型 ⇒ 不含 msiexec、无 Quiet ⇒ 文件名非 uninstall.exe ⇒ `'other'`（与 VERDICT 佐证行「dryRun 明示 installerType=other」**吻合**，说明当次预捕获确实命中了某条键）。此时核验面 = 注册表键消失；**但 portable 真身（Packages 目录 + Links）不在三态判据覆盖内**（`$root` 若取自 `InstallLocation` 空、反推 winget.exe 所在目录=SystemApps 形态失真——`UninstallString` 反推出的目录是 **winget.exe 自身目录**而非包目录！见 :488-495：`GetDirectoryName(exe)`——若 UninstallString 指向 winget 客户端路径，root 即被派生成 winget 目录，dirGone/exeGone 全在核验 **winget 自己的目录**，卸载后当然仍在 ⇒ passed 靠 registryGone 单独把关）。
- **若存在双登记**（早期手动/MSI 装的 `ripgrep` 一条 + winget portable 合成一条，(name,version) 不同 ⇒ inventory 各显一行）：winget 只删自己那条；匹配打分对另一条（GUID 键名/DisplayName 无 `ripgrepmsvc` 归一交集）score=0 不命中 ⇒ `registryGone=true` **成立而 inventory 仍见**——「installDate=20260921 未变」正是残留另一条的指纹候选。
