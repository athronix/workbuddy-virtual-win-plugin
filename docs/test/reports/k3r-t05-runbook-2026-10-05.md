## 1. 灰度开关的切换机制（Route A，已逐跳验证）

不走机器级环境变量，改**运行时配置文件**的 provider options。链路逐跳已核：

1. `delivery/.generated/vm-service.runtime.json` → `agent.providers.workbuddy.options.approvalTruth`
2. `packages/core/src/config/index.ts:242` `providers: { ...defaults, ...parsed.agent.providers }`
   —— provider 级**浅合并** ⇒ `workbuddy` 条目整体来自配置文件，`options` 未知键**原样保留**。
3. `packages/core/src/config/index.ts:201 validateServiceConfig`
   —— 只校验 host/回环、provider 存在性、port、probeIntervalMs，**不拒绝 options 未知键**。
4. `packages/vm-service/src/cli.ts:119` `await factory(entry.options ?? {})`
   —— options 原样交给 `createProvider`。
5. `packages/adapter-agent-workbuddy-llm/src/index.ts:176` / `src/bridge.ts:767`
   —— `opts.approvalTruth ?? resolveApprovalTruth(process.env)`，**显式配置优先**。

**重启用 `C:/WinVMBridge/kill-restart.ps1`**（实测其内容：kill 18443 端口属主 + ps-bridge → `schtasks /End` → `schtasks /Run`）。
**它不重跑 install-vm ⇒ 不会重新生成 `.generated/` ⇒ 手改的配置不会被覆盖。**
（对照：若改用 `deploy-vm.mjs --apply`，install-vm 会**重新生成**运行时配置，手改即失效 —— 所以顺序必须是「先部署，后打补丁，再用 kill-restart 重启」。）

「未复现 ≠ 已修、必须确定性注入」的口径。故必须有**与命中无关**的运行时指纹。

## 3. 执行序列

### 阶段 A｜部署新构建
```
node delivery/deploy-vm.mjs --env=.env.deploy-vm            # 先 dry-run
node delivery/deploy-vm.mjs --env=.env.deploy-vm --apply    # 再真执行
```
判据：脚本末尾 `[VM-START] ✅ VM 服务已监听 127.0.0.1:18443`。

### 阶段 B｜版本指纹（证明跑的是新代码，不是 uptime）
- `GET /health` → `psBridge.uptimeMs` 应**大幅回落**（部署后刚重启）
- `GET /health` → `provider.approvalTruth.mode` 应为 **`on`**（E-3 指纹，缺省 on）
- 补充指纹：`steps[0].risk` 取到 `L2`（旧构建硬编码 `L1`）⇒ 本轮用 `app.winget.uninstall` L2 拦截路径自带

> 只用 uptime 不足以证明版本；指纹 > uptime（既有教训）。

### 阶段 C｜切 `shadow`（D-3 强制轮）
1. 备份：`cp vm-service.runtime.json vm-service.runtime.json.bak-on`
2. 在 `agent.providers.workbuddy.options` 内加 `"approvalTruth": "shadow"`
3. `powershell -File C:/WinVMBridge/kill-restart.ps1`
4. 轮询 `/health` 直到 `ok=true`，**断言 `provider.approvalTruth.mode === "shadow"`**（E-3 指纹）
   —— 断言不通过则**停止**，不得进入测量。

### 阶段 D｜shadow 测量（≥3 次，量化命中率 + 串台率）
```
node qa/r19/a2a-extra.mjs k3r --prefix=/storage/Users/currentUser/wbtmp/k3r-shadow-<N>
```
每次记录：
- 任务终态（`input-required` / `completed` / 其它）
- **`completed` 即一次 K3 假成功样本**（shadow 态下判据不改判，故仍会 `completed`）
- warn 是否出现 `[shadow] 未决审批结构化命中` ⇒ **命中计数**
- 串台核对：结果里的 `approvalId` 是否属于**本委派**的 trace（R2 精确排除的反面证据）
- 对照证据：`/health.provider.approvalTruth.mode` 全程为 `shadow`

产出：命中率 = 命中次数 / 总次数；串台率 = 串台次数 / 命中次数。

### 阶段 E｜切 `on`（根治态复跑）
1. 改回 `"approvalTruth": "on"`（或删键走缺省）
2. `kill-restart.ps1` → 断言 `mode === "on"`
3. 同样跑 ≥3 次 `k3r`

**通过判据（K3 根治成立）**：
- 每个样本终态为 **`input-required`**（而非 `completed`），且 `approvalId` 与服务端 `pendingApprovals` 一致
- 与 shadow 轮同条件对照：shadow 轮的 `completed` 样本在 `on` 轮全部转为 `input-required`
- 未出现 `ok:true` 却未执行的假成功

### 阶段 F｜收尾
- 删除 `.bak-on` 备份前先确认线上为 `on`
- 删除 `C:/WinVMBridge/inspect-vm-env.ps1`（本次巡检临时脚本）
- 汇总写入 `docs/test/reports/`（**每轮只留一份权威报告**）

## 4. 已知坑（本轮已踩 / 既有教训）

| 坑 | 说明 |
|---|---|
| **`k3r` 子命令没有 dry-run** | `qa/r19/a2a-extra.mjs` **任何参数组合都会真的下发一次委派**（曾误以为 `--help` 是试运行，实际发出 L2 卸载任务）。下发即产生真实拦截，须按协议回 `approved:false` 收尾。 |
| 远端 shell = Git Bash(MSYS) | `/` 开头参数被路径转换 ⇒ 远端逻辑一律写 `.ps1` → scp（**远端路径须 `C:/…`**）→ `powershell -NoProfile -ExecutionPolicy Bypass -File` 执行 |
| 配置会被重新生成 | 只有 `install-vm`（即 `deploy-vm.mjs --apply`）会重新生成 `.generated/`；`kill-restart.ps1` 不会 |
| 证据文件「写完再读」 | 读取落在写入窗口内会得到未 flush 的 0B 假空文件；任何"为空"结论须二次确认（mtime + 字节 + 进程存活） |
| 隧道假活 | TCP 通但 HTTP 黑洞时判据是 ping 100% 丢包；`alive=true` 才可信 |
