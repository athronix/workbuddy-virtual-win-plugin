## 一、优化了什么（原架构 → 新架构）

### 1.1 一句话

> **三个执行入口收成一个闸；三个 provider 收成一个执行器 + 一个可选规划器；两套域模型收成一张派生表。**

### 1.2 六处实质变更

| #     | 维度              | 原架构                                                                                                                                 | 新架构                                                  | 为什么必须改                                                                                                                         |
| ----- | --------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **A** | **执行路径**        | `/mcp` 走闸（策略→审批→审计），但 `/mcp/browser`、`/mcp/desktop` 的 **58 个上游工具直接 `handleRequest()`** —— 零策略、零审批、零审计                               | 三面全部汇入唯一 `gateAndExecute()`                          | 这是**安全洞**，不是洁癖：`desktop_click` 点了什么、`browser_eval` 跑了什么 JS，当前**完全无痕**。且 `mcp-upstream.ts` 搜 `policy\|audit\|approval` 命中 **0** |
| **B** | **Provider 抽象** | 3 个 provider（`workbuddy` / `deterministic` / `hermes`）**各实现一遍 `execute()`，但三份 `execute()` 最终都委托给同一处**，差异只在 `runGoal`                | 1 个执行器（恒确定性）+ 可选 Planner（只负责 `runGoal`）              | 抽象层级错了：把「怎么规划开放任务」这个**策略问题**混进了「怎么执行确定动作」这个**安全语义**。3 个包 702+1892 行只为一个可切换的规划能力                                                |
| **C** | **能力表**         | 两套：`WINDOWS_CAPABILITIES`（54，有 risk）+ 上游 58 个**从未被当作能力**（不在注册表 ⇒ 进不了闸、进不了守卫）                                                        | 一张 112 项表（54 + 33 browser + 25 desktop），`surface` 区分 | 没有表就没有 risk，没有 risk 就没有审批判据。「三面未统一」是 A 的前置条件                                                                                   |
| **D** | **域模型**         | `CapabilityDomain`（6 值）与 `SkillDomain`（4 值）双轨，`domains` 字段全仓**零消费**，且**已漂移**（4 vs 6）                                                | 删 `SkillDomain`，域一律从 `id` 派生                         | 同一事实的第二份手写副本，且已经错了 ⇒ 留着只会继续错                                                                                                   |
| **E** | **零消费资产**       | `core/transport/ssh-tunnel*.ts` 690 行（交付链零调用）、`adapter-agent-hermes` 488 行（仅配置出现、零代码 import）、`WINVM_DELEGATION_REQUIRED_POLICY` 双分支 | 全部删除（灰度开关按 owner 裁定保留键名 + 收敛单分支 + 废弃 WARN）           | 死代码会误导：`install-host.mjs` 声明 `kind:'ssh-tunnel'` 但渲染成 `streamableHttp` —— **声明说隧道，产物是 HTTP**                                   |
| **F** | **部署**          | `install-host.mjs` 1655 行，**装 host 还会写通道配置** `vm-conn.json`                                                                         | 抽 `connect-channel.mjs`，装 host 不再碰通道配置               | 消灭职责错位：装插件不该改通道                                                                                                                |

### 1.3 架构图对比（核心差异只有一处：闸）

**原架构** —— 三条入口，只有一条有闸：

```
/mcp          → 54 能力  → evaluateScoped ✅ → provider.execute ✅ → audit ✅
/mcp/browser  → 33 工具  → handleRequest  ❌ 零策略 零审批 零审计
/mcp/desktop  → 25 工具  → handleRequest  ❌ 零策略 零审批 零审计
                            ↑ 58 个工具在这个状态下已上线
```

**新架构** —— 三条入口，一个闸：

```
/mcp          ┐
/mcp/browser  ├→ ★ gateAndExecute()：policy → approval → exec → audit
/mcp/desktop  ┘        ↑ 按 surface 分发执行体，但**先过同一道闸**
```

> **注意**：审批的**位置本来就是对**的（`server.ts:1537` 在 `execute` 之前）。  
> 这次不改位置、不改语义，只**补覆盖面**。owner 在这个判断上是对的（`11` §决策 D）。

## 二、怎么实现（六个阶段 · 22.5d）

### 2.1 阶段与依赖

依赖是**硬的**，不能按优先级重排：

```
阶段 1  删除      3d   纯减法，行为零变化
   ↓
阶段 2  统一      5.5d ★ 112 项能力表（含 3.6a 技能面 +0.5d）
   ↓
阶段 3  闸门      4d   ★★ 安全核心（58 项进闸）
   ↓
         3.6b     +1d  ★ CLI 工具面补齐（必须紧跟阶段 3 之后）
   ↓
阶段 4  降级      4d   provider 3→1（CLI 专职 runGoal，不是删 CLI）
   ↓
阶段 5  解耦      3d   部署层（可与 4 并行）
   ↓
阶段 6  验证      2d   三关 + 真机
────────────────────────────
合计              22.5d （原 21d；+0.5d 3.6a / +1d 3.6b）
```

**为什么是这个顺序**：

| 顺序            | 理由                                                                                          |
| ------------- | ------------------------------------------------------------------------------------------- |
| 删 → 统一        | 留着 `SkillDomain`（4 值）就无法建 112 项分类 —— 会出现「112 项怎么塞进 4 域」的死路                                  |
| 统一 → 闸        | 闸要查表拿 `risk`，表没建好无从查                                                                        |
| **闸 → 3.6b**  | ★ 3.6b 把 `/mcp/browser`、`/mcp/desktop` 的 58 项暴露给 VM 内 CLI。**闸没补就放开 = 给裸奔工具再开一道门**，顺序反了是净增风险 |
| **3.6a 不限顺序** | 技能面是**纯文档**，零执行能力。让 CLI 早一点知道「`browser.*` 该怎么用」不增加任何风险 ⇒ **想先拿一件收益就先做它**                    |
| 降级 在闸之后       | 先让所有路径过同一个闸，再动 provider；否则 provider 改完闸又要重改                                                 |
| 解耦可并行 4       | 只碰 `delivery/`，与 `packages/` 无交集                                                            |
| 验证最后          | 需要前面全部完成                                                                                    |

> 本步一改，这 9 条**必然失败** —— 而门禁不会提前告警，只在跑单测时才炸。
>
> **处置 = 等价搬迁，不是放宽断言**：已实测改后 `winvm` 条目与旧输出**逐字节相等**  
> （因 `base + '/mcp' + search === endpoint`），6 种 dtid×bearer 组合全部为真。  
> 所以改成「`winvm` 单条目逐字相等 + `mcpServers` 恰 3 键」，覆盖面**不减反增**。  
> **9 处必须与实现同 commit**：只改实现 ⇒ 单测必红；只改测试 ⇒ 测试失去意义。
>
> ⚠ 这也是「3.6b 必须等阶段 3」的**又一条**理由：它同时改动 1 个实现文件 + 2 个测试文件的

## 四、施工中发现的问题（原方案需要修正的 3 处）

### 4.1 ⚠ **方案的「自证设计」不成立**（最重要，须 owner 知道）

`13-OPTIMIZATION-PROPOSAL` §4.5 与 `14` Step 3.2 都写着：

> 「阶段 3 做完，基线那 2 个红**应该变绿** —— 因为 58 项已进统一表」  
> 「如果阶段 3 做完基线还是红，说明统一表没真正生效。」

**实测这个推论是错的**：

| 基线红                         | 真实判据                                                                                                                                                                   | 阶段 3 会转绿吗                                            |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| `phase2-snapshot-truth`     | 它数的是「全仓 src 里出现 `snapshot` 字样的**文件集**是否等于白名单」。`mcp-upstream.ts` 有 2 处命中：`:89` 的 `'desktop_snapshot'` **和 `:65` 的注释**「snapshot / find / screenshot…」                    | ❌ **不会**。即使把白名单常量搬走，第 65 行注释仍命中 ⇒ 该文件仍在 hits 集合 ⇒ 仍红 |
| `phase3-skill-claims-guard` | 它的 `registeredIds()` **从 `definitions.ts` 源码正则提取**，不读统一表。offender 是 `agent_browser_eval.md:37` 的 `response.data.unserializable` —— 这是**上游 vendor 文档里的返回值字段路径**，不是能力 id | ❌ **不会**。把它加进注册表/统一表都不影响它                            |

⇒ **结论**：这两条红不是「三面未统一」的证据，而是**两个守卫件自身的白名单没跟上**。  
把它们当「阶段 3 的自证点」会导致：阶段 3 做完发现还红 → 误判「统一表没生效」→ 白折腾。

**正确处置**（两条独立的小修，与阶段 3 无关）：

1. `phase2-snapshot-truth`：把 `packages/vm-service/src/mcp-upstream.ts` 加入 `WHITELIST`，  
   **理由写清**「同词异物：`desktop_snapshot` 是上游工具名字面量，不是 `audit.snapshot` 策略消费」。  
   （注意：白名单里已有 9 个同类「同词异物」先例，这是第 10 个）
2. `phase3-skill-claims-guard`：把 `response.data.unserializable` 加入 `TOKEN_WHITELIST` 的  
   「④真实字段路径」类，**或**改上游文档措辞。

> **这不违反「不许放宽断言让门禁变绿」的纪律**：那条规定禁止的是「把 `mcp-upstream.ts` 加进豁免名单」，  
> 而这里正是它的反面 —— 现有白名单机制**就是为同词异物设计的**，加一条并写清理由属于正常维护。  
> 关键是：**加白名单 ≠ 关闭守卫**，守卫对新增文件仍然有效。

### 4.2 ⚠ **阶段 2.4 有分层死结**（计划已预见，但理由写错了）

`desktop` 白名单 `DEFAULT_DESKTOP_TOOL_ALLOWLIST` 现在住在 `vm-service`，  
而 `vm-service/package.json` **已依赖** `@winvm/vm-capabilities` ⇒ 反向 import **成环**，dep-lint 必拦。

**计划笔误订正**：原文写「`vm-capabilities`（L3）不能依赖 `vm-service`（L4）」——  
实测两者 `package.json` 里**都是 `L2`**（`L2-vm-capabilities` / `L2-vm-service`）。  
真正依据不是 layer 号，而是现存的 `dependencies` 方向。

**解法**（2.4 动工前须先做，**待 owner 定 A/B**）：

- **A（推荐）**：把常量下沉到 `vm-capabilities/src/registry/`，`mcp-upstream.ts` 从那里 import —— 改一处 import + 一处 re-export
- B：下沉到 `contracts`（更彻底，但 contracts 目前不含任何工具名清单）

本次**没有临时绕过**（在 `vm-capabilities` 硬编码 25 项 = 把可达面抄成第二份事实源，正是要避免的漂移源）。
