🖥️ 用 WorkBuddy 完全操控 Windows 虚拟机 · 方案对比与推荐架构

面向目标：通过宿主机 WorkBuddy 操作 Windows 虚拟机，覆盖系统管理 / 应用管理 / 存储管理 / 图形化应用（桌面、浏览器）。
调研日期：2026-08-28 · 依据：Windows MCP（windows-mcp / win-cli-mcp）、A2A v1.0、MCP 传输安全、Windows 会话隔离机制。
🎯 一句话推荐
以 方案 1（MCP 连接器）为底座 承担 90% 的命令行/系统/存储乃至 GUI 操作； 再 叠加方案 3/4（虚拟机内 Agent + A2A 桥） 作为「高阶自主执行层」，专攻多步骤、强 GUI 的任务； 方案 2（Skill）只作配套知识，不担主渠道。 传输优先用 ssh 隧道跑 MCP stdio（不开端口、SSH 管鉴权加密）；需要多客户端/生产化再上 Streamable HTTP + 令牌/TLS。

一、4 个候选方案逐条评估

方案机制GUI 覆盖（桌面/浏览器）自主性 / 透明度安全 & 复杂度结论
1. MCP/CLI
连接器		 虚拟机内起 MCP server（如 windows-mcp 做 UI 自动化+PowerShell，win-cli-mcp 做受控多 shell）；宿主机 WorkBuddy 作为 MCP 连接器直接调 tools。 ✅ 可覆盖
前提是 MCP 进程运行在「交互式会话」内（见第三节），否则截图黑屏。		 透明度高、可控性强；但需宿主机逐步下指令，长任务往返较多。 契合 WorkBuddy 连接器模型；可加命令/路径白名单；复杂度中。 推荐底座
2. Skill
而非连接器		 把「如何 SSH / 用 CLI 操作虚拟机」写成 Skill 指引，靠 prompt 让宿主机去执行。 ❌ 弱
Skill 无法稳定维持远程连接、难以把截图作为 tool 结果回传。		 无结构化 tool schema，会话管理脆弱。 实现简单，但不可靠；不适合做主控制面。 仅作配套
3. 虚拟机内
Agent + 桥接连接器		 在虚拟机部署 Agent（Hermes / WorkBuddy / 自研），其桥接服务包装为 WorkBuddy 连接器；宿主机把任务委派给虚拟机 Agent 自主完成。 ✅✅ 最佳
Agent 就在虚拟机里、原生拥有 GUI 能力（看屏幕+发输入），天然覆盖桌面与浏览器。		 自主性最强；但宿主机对具体步骤可见性降低（需靠 artifact 回传）。 多跑一个完整 Agent（耗资源）；桥接为自定义协议；调试跨 Agent 较难。 高阶执行层
4. A2A 服务
+ Skill		 同 3，但桥改用 A2A 协议（Agent Card 发现、Task 生命周期、artifact、流式）；宿主机侧配一个「Windows VM 操作」Skill 作指引。 ✅✅ 同 3 标准化、可观测（Task 状态/artifact/trace），未来可替换实现。 比自定义桥更规范，但需两侧 A2A SDK，实现量更大。 桥接首选协议

二、关键约束：GUI 必须运行在「交互式会话」

⚠️ 这是所有方案成败的分水岭，也是最容易踩的坑
  • 会话隔离（Session 0）：Windows 服务默认跑在 Session 0（无图形界面），截图会得到黑屏、模拟键鼠会 Access denied。GUI 自动化必须在 Session 1+ 的交互式桌面（WinSta0\Default） 中运行。
  • RDP 断开即「失明」：远程桌面一点 X 断开，会话被挂起为无头状态，UI 自动化立刻失效。解决：用 tscon 把会话交还物理控制台；或接「虚拟/物理显示器」让会话始终处于 active；或配置自动登录 + 禁休眠。
  • 落地要求：承载 GUI 的控制进程（MCP server / Agent）必须作为用户会话进程启动（登录时自启、或「仅在用户登录时运行」的计划任务、或托盘程序），不能注册成系统服务。
分层建议（与约束对应）：
  • 控制面（CLI/系统/存储）：无需显示，可跑在服务/SSH/任意会话，最省心。
  • GUI 面（桌面/浏览器）：必须跑在活跃的交互式用户会话内，并确保该会话不被挂起。

三、推荐架构：分层混合（1 + 3/4）

为什么这是「更好」的方案：
  1. 不强迫跑完整 Agent：只想跑条 PowerShell、查个磁盘，直接走 MCP 连接器（方案 1），透明、可复现、省 token。
  2. 不丢失 GUI 能力：控制面与 GUI 面都尊重交互式会话约束，桌面/浏览器真能操作，而非只有黑屏。
  3. 标准协议、可维护：工具层用 MCP（纵向连工具），委派层用 A2A（横向连 Agent），避免厂商锁定；两者均为 2026 生产级标准。
  4. 安全内建：默认 ssh 隧道不开端口；或 Streamable HTTP 配令牌+TLS+Origin 校验；win-cli 可做命令/路径白名单与日志。
  5. 按需升级：先上底座（当天可用），GUI 重/多步骤任务再叠加虚拟机 Agent + A2A。

四、传输与安全选项

方式适用安全要点
ssh 隧道 → stdio
连接器 command=ssh vmuser@vmip uvx windows-mcp serve		首选：本地/私有 VM、单客户端无需开端口；SSH 密钥鉴权 + 加密；VM 开 OpenSSH Server。简单且安全。
Streamable HTTP
VM 内常驻 MCP 端点（如 /mcp）		多客户端 / 生产化必须 HTTPS(TLS1.3)+ 令牌(mTLS/bearer)；校验 Origin 防 DNS 重绑；绑定内网/VPN，绝不裸奔公网。
A2A（方案 4 桥）Agent 间委派Agent Card 描述能力+认证；HTTPS；任务态可观测、可取消；human-in-the-loop 审批高危操作。

五、风险与缓解

  • 等于给 VM 开 RCE：Windows 控制 MCP 权限极高 → 强制令牌/SSH 鉴权、命令&路径白名单、仅限内网、全量日志；高危操作（删/格式化/关机等）加人工确认。
  • GUI 黑屏/失效：控制进程跑在用户会话 + 保活（自动登录 / tscon 归还控制台 / 虚拟显示）；RDP 用 tscon 断连而非直接 X。
  • 委派「黑盒」：虚拟机 Agent 必须回传 artifact（截图、日志、变更清单），保持宿主机可见；重要动作设审批闸。
  • 资源占用：虚拟机 Agent 吃内存/CPU → 仅在需要时启动，或常驻低配。

六、落地路线图（建议先到后）

  1. Day 1 · 底座验证：VM 内装 uv/Python，跑 uvx windows-mcp serve，测截图/启动应用/PowerShell 工具。
  2. Day 1 · 会话保活：配置自动登录或保持控制台会话 active，确认截图非黑屏。
  3. Day 1 · 连接器接入：宿主机 WorkBuddy 加 MCP 连接器（ssh stdio 方式），测一次工具调用。
  4. Day 2 · 加固：叠加 win-cli-mcp-server 做受控 shell（命令/路径白名单、日志）。
  5. Day 3+ · 高阶（可选）：VM 内部署 Agent，暴露 A2A Server（Agent Card）；宿主机用 A2A 客户端委派长任务；配套「Win VM 操作」Skill 沉淀最佳实践。
