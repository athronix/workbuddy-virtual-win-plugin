## 1. 一句话背景

项目为「宿主机 WorkBuddy（AI Agent）」开发插件，使其完全操作一台 Windows VM。上一轮（T06–T09）已落地宿主侧鸿蒙适配；本轮场景为 **宿主 = 本机鸿蒙（HMOS）WorkBuddy，VM = 本机 Windows 虚拟机（`ssh User@172.16.100.2`）**，目标是**收口 + 补齐最后一公里**：让「装完即可用」这条路真正走通，并把文档债还清。

**「最后一公里」的准确含义**：上一轮解决了「代码能不能在鸿蒙上跑」，本轮解决「**装完之后，用户什么都不做，`connector:winvm` 能不能连上**」。

## 3. 需求详情

### CL015-P0-01 · 第三方运行时依赖（ssh2）离线分发链路

**现状事实（已实测，直接采信）**
- `packages/core/package.json` 运行时依赖含 `ssh2@^1.16.0`。
- `delivery/install-host.mjs` 的 `collectWinvmDeps()` **显式跳过所有非 `@winvm/*` 依赖**，其注释仍声称「本仓库 @winvm 包运行时零第三方依赖」——该断言**已过时且错误**。
- 后果：安装后插件缓存 `node_modules/` 内**没有 ssh2** → 鸿蒙宿主上任何 `import('ssh2')`（`delivery/oh-tunnel.mjs`、`packages/core` 的 ssh2 隧道后端）**必然失败** → ssh2 隧道（鸿蒙无系统 ssh 时的**唯一通路**）起不来。
- 仓库当前**无 `vendor/` 目录**、无任何 ssh2 预置产物。

**用户价值**
用户不需要理解 npm、不需要联网、不需要手动拷包：安装器跑完，ssh2 就在该在的地方，隧道就能起。

**验收标准（可观测、可判定）**

| # | 验收项 | 判定方式 |
|---|---|---|
| A1 | 安装成功后，插件缓存根内 `node_modules/` **离线可解析 ssh2** | 宿主**断网**条件下，从插件缓存根以 Node 解析 `ssh2` 成功（解析结果路径存在，且其 `package.json.name === 'ssh2'`）→ PASS |
| A2 | 鸿蒙宿主上隧道**不再因缺包失败** | 宿主侧建立隧道时 `127.0.0.1:18443` 监听成功，全过程**无** `Cannot find module 'ssh2'` / `ERR_MODULE_NOT_FOUND`（**回归红线**：出现即 FAIL） |
| A3 | 缺失时的引导**可执行**，且不再有错误断言 | 人为移走缓存内 `node_modules/ssh2` 触发降级：输出**同时包含**①缺失包名 ②期望落点路径 ③一条可直接复制执行的修复动作；且源码内「本仓库 @winvm 包运行时零第三方依赖」类过时注释已消除 |
| A4 | **幂等**：重复安装不破坏、不重复膨胀 | 连续两次安装均成功；第二次后 `node_modules/ssh2` 仍可解析，且不出现重复/嵌套副本 |
| A5 | Windows/macOS 宿主**零行为变化** | win32/darwin 下隧道后端仍为系统 `ssh`、连接器渲染结果与本轮前一致；新增的依赖落地不改变既有安装成功判定 |

**依赖与约束**：分发方式（仓库内 vendor vs 发布产物内预置 vs 安装期联网）属实现选择，见 §6 开放问题 1；但**离线可解析**是硬性验收，不接受「要求用户联网」作为唯一路径。

### CL015-P0-02 · 常驻隧道入口（daemon）

**现状事实**
- `connector:winvm` 为 `streamableHttp → http://127.0.0.1:18443/mcp`，**要求 127.0.0.1:18443 在宿主侧常驻可达**。
- 现有 `delivery/oh-tunnel.mjs` **只有进程内隧道**（521 行，仅导出 `establishSsh2Tunnel`，**无 CLI / 无 `--daemon` 入口**）：由 `delivery/setup.mjs` 在部署期建立、部署进程退出即清理；`delivery/winvm-plugin.mjs` 为单次命令临时建立、命令结束即拆。
- 后果：**部署完就没有隧道了** → WorkBuddy 用 `connector:winvm` 时连接必然被拒。鸿蒙又无系统 `ssh`，无法靠 `ssh -f -N -L` 常驻。

**用户价值**
用户装完之后可以直接去 WorkBuddy 里用 `connector:winvm`，不需要知道「还得先手动挂一条隧道」。

**验收标准（可观测、可判定）**

| # | 验收项 | 判定方式 |
|---|---|---|
| B1 | **安装后自动可用**（零人工动作） | `install-host.mjs --apply` 成功返回后，不改任何配置、不再敲任何命令，宿主侧对 `127.0.0.1:18443` 的回环 TCP 连接立即 **OPEN** |
| B2 | 提供三个生命周期动作：**启动 / 查询 / 停止** | 三个动作均可独立调用并有明确输出；「查询」输出**运行中/未运行 + 监听地址 + 端口 + 目标 VM**，且其状态与真实端口可达性**始终一致**（运行中→可连；未运行→不可连；**无假阳性**） |
| B3 | **重复启动幂等** | 连续两次启动：第二次返回「已在运行」语义（**非报错**）；端口仍只有 1 个持有者，**不出现 `EADDRINUSE`**、不产生第 2 个常驻实例 |
| B4 | **停止干净** | 停止后 `127.0.0.1:18443` 变为**不可达**，无残留监听；紧接再启动**立即成功**（无 `EADDRINUSE`） |
| B5 | **卸载自动停止** | `install-host.mjs --uninstall --yes` 后隧道**自动停止**，`127.0.0.1:18443` 不可达，且端口无被遗留进程占用 |
| B6 | **断线自愈** | VM 侧服务短暂不可达后，隧道在恢复后**无需人工干预**即可再次连通；期间「查询」如实反映不健康（不谎报健康） |
| B7 | **安全红线**：仅绑回环 | 监听地址**只允许** `127.0.0.1` / `::1`；出现绑定 `0.0.0.0` 或任何非回环地址即 **FAIL** |
| B8 | 重复安装幂等 | 连续两次安装不产生第 2 个常驻实例、不重复写入（与 B3 同一幂等语义，覆盖「安装」入口而非「启动」入口） |
| B9 | Windows/macOS 宿主**零行为变化** | win32/darwin 宿主安装后，进程表与端口状态与本轮前一致（**无新增常驻进程**）；常驻托管的新增行为须经 `process.platform` 守卫隔离 |

**依赖**：B1 依赖 CL015-P0-01（无 ssh2 则隧道起不来）；B1/B6/B7 的真机部分需 VM 侧服务已就绪（基线 P0-R0，属外部前置）。

### CL015-P0-03 · 离线可验证（单测锁）

**用户价值**
「能用」不是靠人肉复述，而是有一条**任何人在无网机器上都能复跑**的证据链；同时把「凭据永不进日志」这条红线从注释变成断言。

**验收标准（可观测、可判定）**

| # | 验收项 | 判定方式 |
|---|---|---|
| C1 | **离线可跑** | 在**无 `node_modules` / 无网 / 禁 `npm install` 与 `npm run build`** 的条件下，本轮新增或修改的测试**逐文件**执行 `node --test <file>` **全部通过**（遵循仓库既有硬约束：**不得整批跑**，规避 `link-workspace` junction 崩溃） |
| C2 | 覆盖 **①凭据红线** | 构造带**哨兵值**的 `password` / `privateKey` / `passphrase`：捕获全部日志与事件输出，断言**不含哨兵值**；异常消息中亦不含 → PASS（对应基线 P1-R9 红线断言） |
| C3 | 覆盖 **②ssh2 解析链** | 无 ssh2 的沙箱下：模块**加载不失败**（惰性/注入式解析）；「缺失 ssh2」路径输出含①包名②期望路径③修复动作三要素 → PASS |
| C4 | 覆盖 **③daemon 生命周期与幂等** | 以假实现（不真连网）断言：启动 → 查询 → **重复启动** → 停止 的状态流转正确；重复启动不产生第二个实例；停止后状态为未运行 → PASS |
| C5 | 覆盖 **④启动器 shell 兼容** | 断言生成的 POSIX 启动器在 **`sh`** 下执行退出码 0 且参数透传正确；`bash` 存在时同样可执行 → PASS |
| C6 | 测试不得联网、不引入新依赖 | 断网执行全绿；本轮不新增任何运行时依赖 |

### CL015-P1-01 · POSIX 启动器 shell 兼容

**现状事实**
- 鸿蒙 WorkBuddy 的 shell 是 **`/bin/sh`**（本机 `user_info` 实测），`bash` 未必存在。
- `delivery/deploy-winvm-plugin.mjs` 生成的 POSIX 启动器 shebang 为 **`#!/usr/bin/env bash`** → 只有 `sh` 的环境**会失败**（设计文档已列为风险 4.5）。
- 现有 PATH 注入目标为 `~/.bashrc` / `~/.profile`（均非 `sh` 登录/交互的必然来源）。

**用户价值**
用户在鸿蒙终端里敲 `winvm-plugin` 能命中、能跑，不必先知道「我这台机器有没有 bash」。

**验收标准（可观测、可判定）**

| # | 验收项 | 判定方式 |
|---|---|---|
| D1 | **`sh` 下可执行** | 在屏蔽 `bash`（仅 `/bin/sh` 可达）的环境中执行 `winvm-plugin help`：退出码 0 且输出帮助内容 → PASS |
| D2 | **`bash` 下不回归** | `bash` 存在环境下同样退出码 0、输出一致 |
| D3 | **不依赖 bash 存在** | 启动器首行不再强依赖 `bash` 的解析（D1 通过即为充分证据） |
| D4 | PATH 注入覆盖 **`sh` 登录/交互场景** | 新开一个 `sh` 交互/登录会话中 `command -v winvm-plugin` 有输出（**仅写 `~/.bashrc` 视为不满足**） |
| D5 | 幂等与对称 | 重复安装不产生重复 PATH 条目；卸载**精确移除**本轮注入内容，不误删用户其它 PATH 配置 |
| D6 | Windows/macOS **零行为变化** | win32 仍生成并优先使用 `winvm-plugin.cmd`，用户 PATH 仍走 PowerShell 分支，产物与本轮前一致 |

**依赖**：与 CL015-P0-02 无耦合，可并行。

## 6. 开放问题（需主理人 / 用户确认）
