### 3.1 F-26 根因（实测坐实，非通道故障）

- 现象：`vmcheck` 153s `rc=124`，`vmcheck.log` 只有 `VM_CHANNEL=key…` + `vmssh: ssh2 传输层失败 rc=124（3 试尽）` 两行，载荷 JSON **一个字都没有** ⇒ 极易被误读成「通道彻底不通」。
- 实测：同通道 `ssh2-conn ping` **2.6s** 即 `pong ready`；`vmcheck.ps1` 自身耗时**连测三发 47s / 53s / 56s**（`Get-ScheduledTask` 全枚举 + `Get-NetTCPConnection` 走 `MSFT_NetTCPConnection` + `/health` HTTP 10s + PS 冷启）。
- 根因：`vm-conn.sh` 旧实现只用 `VM_SSH_TIMEOUT=25` 一个变量同时管「连接/握手」与「远端 PowerShell 执行」，每次尝试窗 `25+5=30s` < 载荷耗时 ⇒ **确定性**超窗；而 `-File` 型载荷「跑完才输出」，被 timeout 杀 = 零输出。
- 修复：`vm-conn.sh` 新增 `VM_SSH_EXEC_TIMEOUT`（默认回落 `VM_SSH_TIMEOUT`）与 `VM_SSH_TRIES`；`ps-run.sh` 的 PowerShell **载荷**执行统一经 `_payload` 前缀（`VM_PS_TIMEOUT` 默认 180s、2 试）；`scp`/连接/远端临时件清理仍 25s，语义不被污染。
- 修复后现场复测（默认预算，不抬 `VM_SSH_TIMEOUT`）：`vmcheck` **50s rc=0**；`-c` 重载荷（`Get-ScheduledTask`+`Get-NetTCPConnection`+`Get-Service`）**29s rc=0**。

### 3.2 判据行为什么会被截断

`vm-env-check.ps1` 是「边跑边输出」，被 30s 窗杀掉时前半段（`NODE_FOUND…CLI_OK`）已经吐出来了，**尾部判据行**却丢了 ⇒ 日志看着"像跑完了"，实际没有判据 ⇒ 硬门禁假红。verdict 前置让判据**先于**慢探测（`npm ls -g` cmd 21s / PowerShell 35s）落盘，即使再被截断也能读出结论。

## 7. 遗留与口径

- **仍未覆盖**：`NEED_USER_ACTION=1` 合并包路径（通道坏 → 交用户在 VM 本机跑 `RUN-ME.ps1`）只有静态验证，仍缺一次真机演练（需用户配合）。本轮断言「不得重建通道」的红线被遵守（U3 `kept by request`）。
- **CLIXML 噪音**：`ps-run.sh -c` 的输出仍会夹带 `<Objs …>` progress 流（低优，历史 backlog 项），不影响判据 grep。
- **`VM_PS_TIMEOUT` 不是万能钥匙**：若真出现「载荷 >180s」的探针，显式 `VM_PS_TIMEOUT=300` 传参，**禁**全局抬 `VM_SSH_TIMEOUT`——那会把「传输层真挂起」的快速失败拖成慢失败。
- 口径提醒：`rc=124` + 载荷零输出 = **先量载荷耗时**，不要先怀疑通道；判据见 `references/troubleshooting.md` 新增 G 章。
