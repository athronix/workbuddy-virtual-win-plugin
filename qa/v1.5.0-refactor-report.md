## 1. 用户裁定与落地映射

| 裁定 | 落地 | 关键判据 |
|---|---|---|
| 卸载时 SSH 通道已不在 → 不重建；卸载本身三段（host / vm / ssh 通道），后两件合并给用户 | `undeploy.sh` 三段式 + `channel.sh status` 只判不建 + `build-vm-bundle.sh` 生成四件合并包 | `CHANNEL_UP=0 REBUILD=NO`、`VM_BUNDLE=`、`NEED_USER_ACTION=1`；输出中出现 `ensure`/`host-generate-key`/「重建通道」即违规 |
| 通道仍在 → WorkBuddy 自己卸 VM 端，hos 拆通道脚本设为 VM post 动作 | `vm-remove-local.ps1` 经 `ps-run.sh` 执行；`channel.sh post` 推 hos 模板并以 SYSTEM 计划任务 `WbTunnelRollback` 触发 `-Rollback` | `VM_CLEANUP_DONE` + `TUNNEL_POST_DONE`；会话自断后任务仍跑完 |
| 只有 deploy 保障通道：在则不建，不在才引导 hos 一键脚本；两端部署经通道自动完成 | `deploy.sh` C1 → `channel.sh ensure`；`CHANNEL_EXISTS=1` 直接过，否则打印粘贴脚本并 `DEPLOY_NEED_USER_ACTION=1` rc=2 | `channel.sh confirm` 四段验收 + `ssh2-conn.mjs ping` 权威复核 |
| verify 在 deploy ready 后由 WorkBuddy 自调，做健康/功能性监测 | `verify.sh` 不建/不修通道；统一 ssh2 与 `VMDEPLOY_RUN_DIR`；通道瞬态窗标 `ENV_WINDOW=1` | `VERIFY=PASS` / `VERIFY=FAIL` / `VERIFY=INCOMPLETE rc=2` 三态，无假绿 |

## 7. 误报风险与未完成项（如实声明）

1. **真机 E2E 未跑（最高优先级风险）**：本轮全部证据是静态/本地/发布链，未触碰 VM。v1.5.0 三条新路径——① 通道坏 → 用户执行 `RUN-ME.ps1` 合并包；② 通道在 → VM SYSTEM 任务 `WbTunnelRollback` 在 ssh 会话断开后完成回滚；③ `roundtrip.sh full` 判稳 gate 与 `--keep-tunnel` 往返——**都还没有真机证据**。尤其 ② 属于「自断会话后异步执行」，只能靠真机验证。
2. **母项目 V1.4.27 pack 未执行**：本次发布的是 skill 仓自身 release zip；随母项目 tag 分发的 `winvm-plugin-deploy-skill.zip` 仍需一次 pack（会同时收编 R5 运行码）。pack 源 symlink 已生效、白名单会自动收新脚本，但**未实跑 pack 断言**，不能宣称该资产已产出。
3. **gh scope 元数据与实证不一致**：`gh auth status` 显示 scopes 仅 `gist/read:org/repo`（缺 workflow），但 dispatch 实际 `ok=true via:gh`、sync run success、marketplace 版本追平、Gitee HEAD 一致。判定以四重实证为准；后续若 dispatch 转 403，`skill_dev.py` 内置 REST 降级 + 每日 cron 兜底，需如实报告而非谎称同步。
4. **未覆盖的旧审计项**：F-01（U5 存留项脚本化）、F-06、F-12~F-16 及 `act-*.sh`/`winvm-flow.sh` 全量动作层重划分本轮未做；采用「保留既有 driver、新增单一动作层」的最小改造路线，以保 pack V11 断言与既有调用面兼容。
5. **母项目工作树**：`qa/audit-2026-11-13-deploy-flow.md`、本报告、` .workbuddy/memory/` 两份为未提交状态（按 `skill-dev-git` 纪律，skill 内容不得混入母项目提交；这些属母项目自身文档，未擅自提交）。
